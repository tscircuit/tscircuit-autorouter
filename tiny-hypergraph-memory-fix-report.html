The Fix Was Not “Optimize More”

The big memory win came from changing the shape of one solver data structure. Tiny Hypergraph was allocating A* best-cost arrays as if every port could hop to every region. In practice, each port can usually hop to only one or two incident regions.

What Was Actually Wrong

The core bug was not “too many objects in general.” It was one very specific mismatch between the solver’s memory model and the graph’s topology.

Old assumption

“For a hop, index best-cost storage by `portCount * regionCount`.”

Real topology fact

“A port’s `nextRegionId` is almost always one of that port’s incident regions, usually at most 2.”

Ports

14,461

Regions

1,802

Reachable Hop Slots

~29k

That means the old dense arrays reserved space for about 26 million port/region combinations even though only about 29 thousand were reachable. Almost all of the memory was dead space.

The Big Data Structure Change

Before

hopId = portId * regionCount + nextRegionId

Fast indexing, but it assumes every `nextRegionId` is relevant for every port.

After

hopId = portId * hopSlotStride + incidentRegionSlot

`incidentRegionSlot` is the slot inside `incidentPortRegion[portId]`. The stride is the max incident-region count, typically 2.

Defensive Edge Case

If a hop targets a non-incident region, it gets a negative id and falls back to a tiny overflow `Map`. That preserves correctness without paying dense-array cost for rare cases.

Memory Shape Before vs After

Old best-cost arrays per solver ~312 MiB
New compact arrays per solver ~0.4 MiB

The dense arrays were:

`candidateBestCostByHopId` = `Float64Array` ≈ 199 MiB
`candidateBestCostGenerationByHopId` = `Uint32Array` ≈ 99 MiB

Together they dominated the retained `solveGraph` plateau.

Why Earlier Fixes Helped But Did Not Finish It

1. Duplicate-port prepass copy-on-write

This removed huge constructor-time deep cloning. Good fix, but it only moved the bottleneck from constructor to `solveGraph`.

2. Lazy `inputNodeWithPortPoints`

This stopped the wrapper from holding a second full port-point view during construction. Useful, but still not the dominant plateau.

3. Metadata views with `Object.create(...)`

This reduced churn and preserved behavior, but it was only a micro-optimization once the main structural issue moved into search-state storage.

4. Skip empty `optimizeSection`

This removed dead work and some retention, but the huge A* table was still alive.

The Other Important Part: Release State

The compact indexing fixed the biggest allocation. The rest of the improvement came from dropping transient search state as soon as a stage no longer needed it.

`releaseTransientSearchState()` in `core.ts`

Clears `_problemSetup`, the overflow map, `bestSolvedStateSnapshot`, and the candidate queue. These can be rebuilt lazily if needed.

Pipeline `onSolved` hooks

`solveGraph` releases its transient state after finishing. `optimizeSection` does the same and clears cached stage params.

Section solver release

Once an optimized solver exists, the section-level search solver and snapshots are dropped instead of being retained for no reason.

The Fix In Plain English

Think of the old solver as renting a giant parking lot with one parking spot for every possible port/region pair, even though each car was only allowed to park in one or two specific spots.

The new solver keeps only the spots that are actually reachable for that port. That cuts the best-cost table from hundreds of MiB to well under a MiB.

Then, after a search stage is done, the solver throws away temporary notebooks: candidate queues, snapshots, heuristic caches, and other scratch state that were only needed during search.

So the final answer is: the fix works because it changed the solver from storing costs for impossible hops to storing costs only for incident-region hops, and then it stopped retaining temporary search state after solve.
