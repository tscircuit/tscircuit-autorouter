# Shared module allocator

This private crate supplies the global allocator for `autorouter-bindings` and `tiny-hypergraph-bindings`. Each module has its own allocator and linear memory; they share the implementation, not allocated blocks. Native builds retain their existing allocator.

The allocator uses `dlmalloc` 0.2.14 with an **8 MiB system-allocation granularity**, configured before the first allocation. Small Rust allocations still receive their requested sizes. When more linear memory is needed, dlmalloc obtains larger regions and reuses freed blocks within them, reducing the number of `memory.grow` calls. See [`Dlmalloc::set_granularity`](https://docs.rs/dlmalloc/0.2.14/dlmalloc/struct.Dlmalloc.html#method.set_granularity).

This addresses a JavaScript runtime boundary cost. Growing non-shared WASM memory invalidates its fixed-length buffer wrapper, and generated bindings subsequently obtain a refreshed buffer and typed-array views. WebKit's [`JSWebAssemblyMemory::growSuccessCallback` and buffer construction](https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/wasm/js/JSWebAssemblyMemory.cpp) implement that lifecycle; [`JSArrayBuffer::finishCreation` and `estimatedSize`](https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/runtime/JSArrayBuffer.cpp) connect wrappers to GC accounting. Frequent growth can therefore create collection pressure beyond the amount of newly added linear memory. GC allocation-accounting totals are not physical bytes copied or peak resident memory.

The implementation is restricted to single-threaded `wasm32-unknown-unknown` modules. Builds with the `atomics` target feature fail at compile time. Its `UnsafeCell` access relies on one thread and on dlmalloc's WASM system allocator not calling user code during allocation; it is not suitable for shared-memory or threaded WASM. Reentrant JS callbacks elsewhere in a solver do not overlap an allocator operation.

Larger growth increments trade fewer runtime transitions for additional unused linear-memory capacity. Freed blocks remain reusable inside the module; freeing a solver does not shrink its linear memory. Requests near a host or module memory limit can fail when the larger growth request cannot be satisfied. Allocation failures retain normal Rust allocation-failure behavior; there is no alternate routing backend or recovery policy.

This changes allocation behavior only. Routing algorithms, candidate ordering, numerical operations, cache keys, and public solver APIs remain unchanged. Runtime effects should be assessed with matched whole-dataset benchmarks and exact output comparisons, rather than extrapolated from a single board.
