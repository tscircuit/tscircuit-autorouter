Report on what must change so high-density solvers use prevPortPointId and nextPortPointId to decide which port points belong together, instead of inferring pairs only from grouping or array order.

Missing From First Draft

Legacy Risk Area

Autorouter intra-node subsolvers

Several non-`a01` autorouter subsolvers still form route work units by `connectionName` grouping.

Bottom Line

The repo is partway there already. The shared helper getConnectionPortPointPairs reads prevPortPointId and nextPortPointId and produces explicit point pairs.

`A01`, `A02`, `A03`, and `A05` already call that helper when they build connection segments, so those solvers are effectively chain-aware today.

The main solver that still needs a real behavioral update is HighDensitySolverA09. It groups every port point by connectionName and routes each group as if it were one two-ended connection, which breaks down when a single connection name contains multiple linked port-point segments.

Why A09 Is The Problem

  • `A09` builds a `Map<connectionName, ConnectionInfo>` instead of building explicit linked endpoint pairs.
  • That means four port points with the same `connectionName` can be treated as one logical connection group, even if the chain metadata says they belong to two separate segments.
  • The downstream ordering and subproblem routing logic then reasons about the wrong unit of work.
  • If `prevPortPointId` and `nextPortPointId` are supposed to be authoritative, `A09` must stop using `length >= 2` as the connection-definition rule.

What Is Already Good

  • The shared helper already resolves pairs by `prevPortPointId` and `nextPortPointId`.
  • `A01`, `A02`, `A03`, and `A05` already call that helper at segment-build time.
  • `A08` delegates to `A01` for the inner-node solve, so it benefits automatically once chain metadata is preserved on copied points.
  • The repo does not need a broad rewrite; the main behavior gap is localized.

Recommended A09 Refactor

  1. Replace getConnections() with a builder that first groups by connectionName, then runs getConnectionPortPointPairs() inside each group.
  2. Convert each returned pair into its own `ConnectionInfo`-like unit, rather than keeping all same-name points in one bucket.
  3. Preserve rootConnectionName on each pair unit so ordering and scoring still understand sibling nets.
  4. Keep `makeSubproblem()` cloning full `PortPoint` objects with spreads, since that already preserves the chain fields.
  5. Decide whether the fallback in getConnectionPortPointPairs() should remain: if chain links are mandatory, missing links should become a test failure instead of a silent adjacent-order fallback.

Recommended Autorouter Follow-Up

  1. Leave HighDensitySolver.ts as the orchestrator, but document that any delegated solver must accept chain-defined pairing.
  2. Introduce one shared autorouter helper equivalent to getConnectionPortPointPairs, or reuse the same logic locally, so all non-`a01` intra-node solvers form identical route units.
  3. Update `SingleTransitionIntraNodeSolver`, `SingleTransitionThroughObstacleIntraNodeSolver`, `SingleLayerNoDifferentRootIntersectionsIntraNodeSolver`, and `IntraNodeSolverWithJumpers` to consume explicit linked pairs instead of raw `connectionName` groups.

Suggested Test Coverage

  • A01/A02/A03/A05: one `connectionName` with four points linked as two disjoint pairs should produce two independent segments.
  • A09: same fixture should produce two pair-based routing subproblems, not one four-point aggregate connection.
  • A08: breakout-generated inner-node copies should keep `prevPortPointId` and `nextPortPointId` intact before delegating to `A01`.
  • Autorouter legacy solvers: the same four-point fixture should create two route tasks in `SingleTransition*`, `SingleLayerNoDifferentRootIntersections*`, and jumper-based flows.
  • Helper behavior: missing or partial chain metadata should either fall back intentionally or fail intentionally, but the behavior should be explicit and tested.

Practical Conclusion

If the goal is “make the high-density solvers use prev/next to know which port points connect together,” the repo is not starting from zero. The shared helper and four major solvers are already aligned with that model. The highest-value code changes are to refactor `HighDensitySolverA09` and the legacy autorouter intra-node solvers so they stop treating all same-name port points as one connection and instead use chain-defined pairs as their routing unit.
