Bugreport71: why the bad via cluster happened

The screenshot showed same-net vias and trace geometry crossing in a tight cluster. It was not a different-net DRC failure. The route was electrically valid, but the simplification pipeline left unnecessary vias because one solver treated same-net sibling copper as an obstacle.

Visible Symptom

The center cluster around source net 3 contained a short top-bottom-top detour. Two vias remained close to a same-net sibling route, making the output look like a via crossing trace geometry.

Root Cause

`SingleRouteUselessViaRemovalSolver` only ignored conflicts for the exact same route id. It did not use `ConnectivityMap`, so a sibling route on the same electrical net blocked a valid layer move.

Fix

Via removal now receives `connMap` and treats connected sibling routes and obstacles as same-net non-blockers for collision checks. Endpoint layer proof stays stricter and only accepts the actual route endpoint.

Change Story

The route was not broken, it was being protected from the wrong thing

This is the human path through the fix, from screenshot to solver behavior.

Scene 1

The screenshot looked illegal

The cluster had vias sitting right on top of trace geometry. Visually it looked like the autorouter had crossed copper in a way that should never ship.

"Bad thing on screen" did not automatically mean "different-net DRC failure".

Scene 2

The geometry check cleared different nets

I scanned the output routes around that area. The suspicious contacts were same-net or self-route contacts, not collisions between unrelated nets. That changed the question.

Scene 3

The route had a removable detour

The bad-looking route had this shape: start on one layer, drop through a via, run a short section on the other layer, then come back through another via. If the middle section can live on the neighboring layer, both vias are useless.

Scene 4

The solver was too literal

`SingleRouteUselessViaRemovalSolver` asked whether the moved section would hit another route. But "another route" is not the same as "another net". The same electrical net can be split across multiple route ids. 

// old mental model
if (conflictingRoute.connectionName === currentRoute.connectionName) {
  ignoreIt()
}

// missing idea
// route-a and route-b can still be the same electrical net

Scene 5

The fix made via removal net-aware

I threaded the required `ConnectivityMap` into via removal and taught the collision check to treat connected sibling routes as same-net copper. Different-net routes still block the move. 

private routeIsSameNet(route: HighDensityRoute): boolean {
  return (
    route.connectionName === this.unsimplifiedRoute.connectionName ||
    this.connMap.areIdsConnected(
      route.connectionName,
      this.unsimplifiedRoute.connectionName,
    )
  )
}

Scene 6

Then the guardrail got tightened

A review pass caught an important edge: same-net sibling pads are safe to ignore as blockers, but they should not prove that this exact route endpoint supports another layer. So endpoint proof stayed exact while collision checks became net-aware. 

// collision check: same-net is allowed
if (this.obstacleIsSameNet(obstacle)) continue

// endpoint proof: only this route endpoint counts
if (!this.obstacleIsRouteEndpoint(obstacle)) return false

Scene 7

The visible result got simpler

In bugreport71, the source-net-3 center cluster went from two leftover vias to zero. The fix did not hide bad data and did not add a fallback. It made the correct solver understand the actual net relationship.

expect(sourceNet3CenterClusterVias).toHaveLength(0)

Before and After

Full Code Path

  1. fixtures/bug-reports/bugreport71-dd7d15

    The fixture feeds a `SimpleRouteJson` board into `AutoroutingPipelineSolver`.

  2. TraceSimplificationSolver

    The simplification pipeline runs via removal, via merging, and path simplification. The important part is that via removal now receives the same required `connMap` as the other net-aware solvers.

  3. UselessViaRemovalSolver

    This wrapper runs `SingleRouteUselessViaRemovalSolver` once per high-density route and passes `connMap` into each instance.

  4. SingleRouteUselessViaRemovalSolver

    It breaks one route into same-layer sections. If a middle section can move to the layer of both neighboring sections, the two vias around that section are removed.

  5. canSectionMoveToLayer

    This is where the bug lived. Different-net routes still block the move. Same-net sibling routes found through `connMap` no longer block it.

What Was Wrong

The route contained a section like top to bottom to top. That pattern is removable when the middle section can safely live on the top layer.

The old collision check asked: "Does the moved segment hit any route other than itself?" That sounds safe, but it missed a PCB routing detail: different route ids can be part of the same electrical net.

In bugreport71, the only thing blocking the layer move was same-net sibling copper. Because the solver treated that sibling as a blocker, it kept the layer hop and left the visible bad via cluster.

Important Guardrails

  • No fallback was added. `connMap` is a required input where this solver is constructed.
  • Same-net sibling routes are non-blockers only for collision checks during via removal.
  • Endpoint layer proof remains strict. A same-net sibling pad does not prove that this route endpoint can move layers.
  • Via merging remains stricter. It must not merge a via through a sibling same-net route if that would create a visual crossing.
