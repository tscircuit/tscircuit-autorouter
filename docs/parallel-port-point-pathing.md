# WASM-assisted parallel port-point pathing

This implementation preserves the compiled route and blocker searches from the earlier WASM experiment. It is an alternative to the TypeScript-only PRs, with its own dependency pin. The implementation comes from [tiny-hypergraph PR #296](https://github.com/tscircuit/tiny-hypergraph/pull/296). The optional tiny-hypergraph API is isolated in `lib/core-parallel.ts`; its ordinary entry excludes the worker classes and embedded kernels.

Pipeline9 enables it with a verified four-worker Bun or Node runtime. The caller runs the compiled route search and three persistent helpers prepare geometry, region-cost tables, crossing masks and blocker-graph rows. A helper also checks connectivity during long searches; a certified unreachable result can avoid weighted heap expansions while retaining logical iteration accounting. `parallelRouteWorkers: 3` records acknowledged helpers alongside the caller. The worker group is released before later high-density stages, and runtime leases prevent competing groups from overcommitting the same pool.

```ts
const runtime = createAutorouterSolverRuntime({
  workerCount: 4,
  requireWorker: true,
})
const solver = new AutoroutingPipelineSolver9_PreloadedTraceGraph(srj, {
  effort: 1,
  cacheProvider: null,
})
try {
  await solver.solveAsync(runtime)
} finally {
  await runtime.dispose()
}
```

Set `parallelPortPointPathing: false` to use the existing TypeScript solver. A verified one-worker runtime can explicitly select the compiled implementation with `parallelPortPointPathing: true`. Partial-span searches retain their existing implementation. Completion attempts reuse the compiled service and preserve acceptance rules and iteration budgets. Errors and capacity violations propagate.

## Kernels and packaging

The dependency pins tiny-hypergraph `bd47f7205bcc3798919c6dbf9bf857ffe58a2545`, which isolates the previously measured kernel revision behind the optional entry. Checked-in byte arrays make Zig unnecessary for installation or use. Generated modules omit checkout-specific debug metadata; their executable sections match the previously measured kernels, and their generated bytes reproduce across checkout paths. The C++ sources and layout checks remain available under `lib/parallel/wasm/` and can be regenerated with Zig 0.14.1:

```sh
ZIG=/path/to/zig bun scripts/build-route-kernel.ts
```

Rebuild autorouter worker bundles after dependency changes with `bun scripts/build-solver-workers.ts`. Tests exercise both Bun and Node transports. Shared owner graphs and scratch arenas reserve 1 GiB of virtual address space; physical memory usage grows as those structures are populated.

## Measured performance

The earlier exact `/benchmark --dataset 18 --threads 4` comparison is [40452787870](https://github.com/tscircuit/tscircuit-autorouter/actions/runs/40452787870). It measured autorouter `0f4e2d58` with tiny-hypergraph `fd1b884`, before the optional-entry isolation retained here. The checked-in [extracted results](benchmarks/parallel-port-point-pathing-blacksmith.json) refer to that historical run. A new run on the separate WASM PR will validate the final dependency and integration; the historical numbers are not presented as a measurement of the new PR revision.

Both revisions ran sequentially on one Blacksmith 8-vCPU ARM runner with Bun 1.4.2. All times below sum all 16 dataset18 boards.

| Measurement | Base, four threads | WASM implementation, four threads |
| --- | ---: | ---: |
| Port-point phase | 145.594s | 81.198s |
| Total routing elapsed | 571.068s | 487.441s |
| Solved / DRC passed | 16 / 16 | 16 / 16 |
| Timeouts / DRC issues | 0 / 0 | 0 / 0 |
| Peak resident memory P90 | 2613.8 MiB | 5785.9 MiB |

The phase improved **1.793x**, with 44.2% less time; overall time fell 14.6%. The ideal **2x target was not met**. Every board recorded three acknowledged helpers. They prepared 1,022,329 blocker-graph rows, 11,737,555 geometry pairs, 283,113 region-cost tables and 192,605 crossing masks. Connectivity checks avoided 1,096,375 physical A* expansions while preserving logical expansion budgets.

These gains combine compiled execution, data-layout changes and helper work. A historical local compiled-one-worker versus compiled-four-thread control measured only 1.013x, so useful thread scaling has not been established. It used a different Bun version and machine from Blacksmith and cannot isolate the contributions in the full benchmark. Memory usage increased substantially.

The WASM integration defers graph initialization to overlap helper startup. The pipeline's phase clock excludes the base constructor but includes that deferred initialization in the accelerated phase. The earlier phase totals are unadjusted and include that extra initialization work on the WASM side.

Run fresh benchmarks on Blacksmith per repository policy. The command `/benchmark --dataset 18 --threads 4` runs both revisions in the same job and checks full downstream routing and DRC. The phase diagnostic `scripts/benchmark/port-point-threading.ts` also supports `--reference-threads 1 --threads 4 --isolate` for a compiled one/four-thread comparison, and checks status, output hashes and iteration counts. Phase-only checks do not establish downstream DRC outcomes.
